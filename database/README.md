# BuildTrack database

BuildTrack currently runs as a static browser application. Its controllers read and write LocalStorage; this SQLite database is a backend foundation and is not connected to the browser UI. It uses Python's built-in `sqlite3` module, so there are no extra dependencies.

## Setup on Windows

From the project folder in PowerShell:

```powershell
python --version
python -m database.init_db
python -m unittest database.test_db -v
```

The default database is `database/buildtrack.sqlite3`. Initialization is safe to repeat: it creates missing tables/indexes/views and does not clear existing rows. It creates an empty database; it does not copy demo or browser LocalStorage data.

## Run the Projects API

Flask is the API's only external Python dependency. From the project folder in PowerShell, install it and start the development server:

```powershell
python -m pip install -r requirements.txt
python -m database.init_db
python -m api.app
```

The API listens at `http://127.0.0.1:5000`. The app initializes or upgrades the configured SQLite database when it starts. This initial API handles projects only and does not connect the frontend to the API.

### Routes

| Method and path | Purpose | Success response |
|---|---|---|
| `GET /api/projects` | List projects | `200`, `{"projects": [...]}` |
| `GET /api/projects/<id>` | View one project | `200`, `{"project": {...}}` |
| `POST /api/projects` | Create a project; ID is generated by the server | `201`, created project and `Location` header |
| `PUT /api/projects/<id>` | Replace editable project fields | `200`, updated project |
| `PATCH /api/projects/<id>` | Update only supplied fields | `200`, updated project |
| `DELETE /api/projects/<id>` | Delete an unreferenced project | `204`; `409` if related records prevent deletion |

Request/response property names follow the frontend's camelCase format: `startDate` and `expectedCompletionDate`. The API validates the frontend's project fields and form rules, including required name/client/location/manager/dates, date order, one of the four project statuses, progress from 0 to 100, and a budget of at least ₹10,000 in ₹5,000 increments. The database-generated `id` and expense-derived `spent` value are read-only. Invalid requests return `400` with field messages; missing projects return `404`; restricted deletion returns `409`; database failures return a generic `500` message without SQL details.

### Try each route in PowerShell

Keep the API server running in one PowerShell window. In a second window, create a project and save its generated ID:

```powershell
$body = @{
  name = "Demo Site"
  client = "Example Client"
  location = "Bengaluru"
  manager = "A. Kumar"
  startDate = "2026-11-01"
  expectedCompletionDate = "2027-11-01"
  budget = 10000
  progress = 0
  status = "planning"
  description = "API practice project"
} | ConvertTo-Json
$created = Invoke-RestMethod -Uri http://127.0.0.1:5000/api/projects -Method Post -ContentType "application/json" -Body $body
$id = $created.project.id
$id
```

Then list all projects, view the new project, replace it with a PUT request, update one field with PATCH, and delete it:

```powershell
Invoke-RestMethod http://127.0.0.1:5000/api/projects
Invoke-RestMethod "http://127.0.0.1:5000/api/projects/$id"
Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/projects/$id" -Method Put -ContentType "application/json" -Body $body
Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/projects/$id" -Method Patch -ContentType "application/json" -Body (@{ manager = "R. Nair" } | ConvertTo-Json)
Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/projects/$id" -Method Delete
```

## Database helper contract for backend developers

The helpers operate on SQLite only; this work adds no Flask endpoints. Use snake_case database column names in helper dictionaries, then convert to the frontend's camelCase names at the API boundary.

- `list_projects()` and `get_project(id)` return project fields plus calculated `spent`. The stored `projects` table does not contain a `spent` column.
- `list_records(table, project_id=None, date_filter=None)` and `get_record(table, id)` are safe reads over the known database tables. Project-filtered materials include unassigned global-yard stock, as the frontend does.
- `save_record(table, fields)` inserts or updates ordinary CRUD rows for projects, tasks, workers, materials, expenses, payments, company settings, and user profiles. It accepts database column names and lets database constraints validate fields. IDs must be supplied for ordinary records; company settings default to singleton ID 1. User profiles receive an auto ID when omitted and are upserted by case-insensitive email. It intentionally rejects stock transactions and progress reports so their related values cannot be changed separately.
- `delete_record(table, id)` deletes UI-managed task, worker, material, expense, payment, or progress-report rows. Worker deletion cascades attendance; material deletion cascades its stock history, matching the UI. Project deletion is routed through `delete_project()` and stays restricted while related rows exist.
- `get_attendance_for_date(date)` and `save_attendance_for_date(date, {worker_id: status})` read/replace one day's attendance map atomically. Valid attendance statuses remain separate from worker availability.
- `stock_in()` / `stock_out()` update material balance and append history atomically. If no project is supplied, the movement uses the material's assigned project when present.
- `save_progress_report()` saves a daily report and synchronizes project progress in one transaction.
- Calculation helpers include `get_financial_summary()`, `get_inventory_summary()`, `get_attendance_summary()`, `get_dashboard_summary()`, `get_expense_chart_data()`, `get_project_chart_data()`, and `get_report_records()`. They read persisted rows; display formatting belongs at the API/UI edge.
- `delete_project()` returns `True` only for a successful project deletion. Restricted deletes raise `ProjectDeletionError` with related-record counts.

Always use `?` placeholders for values when a backend query is not covered by a helper, and perform related writes in `transaction()`:

```python
from database.db import transaction

with transaction() as connection:
    connection.execute(
        "INSERT INTO projects (id, name, client, location, manager, start_date, expected_completion_date, budget, status) "
        "VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)",
        (project_id, name, client, location, manager, start_date, deadline, budget, "planning"),
    )
```

`connect()` enables and checks foreign keys for every connection. `transaction()` commits on success and rolls back if an operation fails. Dates are ISO `YYYY-MM-DD` text. Amounts and quantities are numeric REAL values because the frontend accepts fractional quantity and price values; money should be formatted only at the UI edge. For a larger financial system, agree on integer minor units and currency rules before production use.

`stock_in()` and `stock_out()` change the material balance and create a stock history row atomically. They raise `ValueError` for invalid quantities or insufficient stock and `LookupError` for an unknown material. `save_progress_report()` inserts or updates a DPR and synchronizes project progress atomically. It marks a project completed at 100%; for lower values it preserves the current status, as the frontend does. The frontend skips parent-project synchronization at exactly 0% due to a truthiness check; this known mismatch is detailed in the audit.

`delete_project()` returns `True` when it removes a project with no related records. If dependent rows exist, it raises `ProjectDeletionError` with the related record counts. The foreign keys also use SQLite `RESTRICT`, so direct SQL deletes are rejected even if code bypasses the helper. The helper never deletes or detaches related rows.

## Schema migrations

The database uses SQLite's `PRAGMA user_version`. **Version 5 is current.** A fresh database is created directly at version 5. Existing databases run each missing migration in order: versions 0–4 upgrade through version 5. Migration 1 adds worker availability validation. Migration 2 rebuilds project-dependent tables with `ON DELETE RESTRICT`, preserving IDs, rows, and links. Migration 3 adds frontend project, wage, skill, and material-category validation triggers. Migration 4 adds insert/update triggers that require all stored date fields to be real calendar dates in exact `YYYY-MM-DD` form; fresh databases enforce the same rule with table `CHECK` constraints. Migration 5 rebuilds only `user_profiles`, preserves profile IDs and fields, removes its single-row restriction, constrains role values to the four stakeholder roles, and makes email unique without regard to case. Known legacy labels are mapped to the closest stakeholder role; unrecognized custom role labels become `Contractor / Admin`. Leap days are accepted only in leap years. Examples such as `2026-02-30`, `2026-13-01`, `2024-2-09`, and `02/28/2026` are rejected.

Migration 4 does not rebuild tables or rewrite existing rows. If a legacy database contains an invalid date, initialization emits a warning that lists the affected table, row, and value. The value remains as-is; the migration prevents new invalid dates and invalid edits but does not silently repair history. Such rows must be reviewed and corrected explicitly by the data owner. Initialization refuses a database newer than the code and can be run repeatedly; each migration is applied once. Future schema changes should add a new numbered migration rather than editing an already-applied migration.

## Tables

| Table | Purpose |
|---|---|
| `projects` | Project details, budget, progress and frontend status. Spending is derived. |
| `tasks` | Project work packages, assignee label, dates, priority and stage. |
| `workers` | Worker profile, wage, availability and current project assignment. |
| `attendance` | One status per worker and date. |
| `materials` | Current catalog item, quantity, reorder level, price and supplier. |
| `stock_transactions` | Auditable stock in/out movement with date, project, and notes. |
| `expenses` | Incurred project costs, separate from cash disbursements. |
| `payments` | Vendor/subcontractor disbursements and clearance status. |
| `progress_reports` | Daily diary, progress, turnout, consumption, blockers and next-day plan. |
| `company_settings` | Singleton firm and preference settings, including notification fields. |
| `user_profiles` | Multiple stakeholder profile records with unique IDs and case-insensitive unique emails; not authentication credentials or sessions. |

`project_financial_summary` sums expense vouchers and calculates remaining budget. Payments are not added to expenses, avoiding double counting. The current frontend's demo project `spent` values do not match the limited seeded voucher list; this implementation deliberately treats the voucher ledger as source of truth. `js/data.js` advances project progress from DPRs, and `save_progress_report()` provides an atomic database operation for future backend use.

For the complete field-by-field mapping, UI source files, derived calculations, and known mismatches, see [`FIELD_MAPPING.md`](FIELD_MAPPING.md) and [`DATABASE_AUDIT.md`](DATABASE_AUDIT.md).

The database test suite includes checks against the frontend contract, migration from version 0 and version 2, and repeat initialization. Run the combined database and existing API tests with `python -m unittest discover -v`; tests use temporary SQLite databases and do not modify the default local database.

## Relationships and API guidance

- Tasks, expenses, payments, and progress reports belong to one project. Workers and materials may be assigned to a project, and stock transactions may reference one. Deleting a project is restricted while any such related record exists. Remove the child record through its own approved workflow before retrying project deletion; the database never silently deletes or detaches it.
- The current frontend removes only the project from its LocalStorage array, leaving child entries behind. The database is stricter and rejects deletion when linked records exist. No frontend/API deletion flow has been connected.
- Attendance belongs to a worker and date. Deleting the worker removes its attendance.
- Stock transactions belong to a material; project association is optional. The reusable stock functions record movement and quantity adjustment together in one transaction, and reject a stock-out that would make quantity negative.
- Worker and task assignment fields remain frontend-compatible free-text labels. The frontend task assignee is a team label and is not reliably a worker ID.
- Current risk alerts are calculated on demand by `js/risks.js`; no risk table is added. The implementation uses deterministic rules over current project records, not a trained model.
- No credentials are persisted. The present login is a browser demo and is not safe authentication for a deployed API.

## LocalStorage migration

The browser keys are `buildtrack_projects`, `buildtrack_tasks`, `buildtrack_labour`, `buildtrack_materials`, `buildtrack_expenses`, `buildtrack_payments`, `buildtrack_progress`, `buildtrack_settings`, `buildtrack_current_user`, `buildtrack_attendance`, and `buildtrack_initialized_v2`. The app seeds demo values only when the initialized flag is absent; attendance uses `{date: {workerId: status}}`, and material history is nested under `usageHistory`.

No importer is included, so there has been no LocalStorage migration. Before importing real browser data, export those exact keys, validate all referenced IDs, and import parent rows before child rows in a transaction. Transform nested attendance to rows and `usageHistory` entries to `stock_transactions`; retain an export backup and review duplicate IDs before committing. The seed fixtures are not automatically inserted into the SQLite database.
