# BuildTrack frontend-driven database audit

## Review scope and conclusion

Reviewed the real frontend in `index.html` and `js/` (data store, forms/controllers, dashboard, reports, and risk rules), plus `database/schema.sql`, `db.py`, `init_db.py`, `test_db.py`, `FIELD_MAPPING.md`, and `README.md`.

The relational model has a table for each persistent construction record the UI edits: projects, tasks, workers, attendance, materials, stock movements, expenses, payments, progress reports, company settings, and the active profile. Its financial view avoids duplicate project-spending totals. Database-side CRUD and calculation helpers now cover the frontend modules; fresh schemas and migrations enforce the visible project, wage, skill, material-category, and strict date rules. Version 4 requires canonical, real calendar dates for new and changed date values. No frontend or API files were changed.

The default local SQLite file was at schema version 3 before migration 4 and contains one project. A pre-migration scan found no invalid stored dates; migration 4 preserves all records and relationships without rebuilding tables. `PRAGMA foreign_key_check` reports no violations after migration. Migration tests use temporary databases.

## Database helper coverage

| Frontend need | Database-layer support |
|---|---|
| CRUD reads and writes for ordinary records | `list_records()`, `get_record()`, `save_record()`, and `delete_record()`; identifiers are allow-listed, values parameterized, and schema constraints remain the final validator. |
| Project financial values in project list/chart reads | `list_projects()` / `get_project()` combine project rows with derived spending; `get_project_spending()` and the `project_financial_summary` view provide totals. |
| Daily attendance map read/replace | `get_attendance_for_date()` and atomic `save_attendance_for_date()`. |
| Stock receipts/issues | `stock_in()` and `stock_out()` atomically change current quantity and add history. An omitted movement project now falls back to the material's current project assignment, matching the frontend. |
| Daily reports and completion state | `save_progress_report()` atomically stores the report and updates the project. |
| Dashboard/finance/inventory/wage metrics | `get_dashboard_summary()`, `get_financial_summary()`, `get_inventory_summary()`, and `get_attendance_summary()`. |
| Persisted chart series and report inputs | `get_expense_chart_data()`, `get_project_chart_data()`, and `get_report_records()`; generated CSV/print output remains presentation-only. |
| Restricted project deletion | `delete_project()` and `delete_record('projects', id)`; both preserve the existing RESTRICT behavior. |

## Schema-to-frontend differences and changes

1. **Project budget and dates:** the old schema allowed a nonnegative budget and did not enforce start/completion order. The HTML form uses minimum 10,000 and 5,000 steps, and `projects.js` rejects a start later than completion. New schema `CHECK`s enforce these rules. Migration 3 adds insert/update triggers to existing databases without rebuilding or rewriting their data.
2. **Worker wage, skill, and material category options:** old schema allowed under-minimum/off-step wages and arbitrary skill/category text. The worker form has 12 skill choices and a `min=300`, `step=50` wage; the material form has eight category choices. Fresh schema constraints and migration 3 triggers enforce those exact options for new or changed values.
3. **Legacy values:** migration 3 intentionally does not rewrite or reject historical values merely because they would not pass the current form. It applies checks on new values and edits to the guarded fields. The version-2 migration test verifies this behavior and preservation.
4. **Project deletion:** the browser only removes the project from its LocalStorage collection and leaves child arrays untouched. SQLite uses `RESTRICT` for every project association and `delete_project()` explains which children block deletion. This protects referential integrity and does not cascade or detach children.
5. **Progress at zero / after delete:** the frontend does not update the parent project when a saved report has a zero percentage, and it does not recompute progress after deleting a report. The current database helper synchronizes zero on save and has no report-delete/recompute helper. The expected business rule is not clear from the UI, so this remains explicitly unresolved instead of changing frontend behavior or inventing a rule.
6. **Worker assignment nullability:** the worker form requires a project selection and shows project options only, but its data layer does not independently validate project presence, and an empty project list can produce no selection. Database assignment remains nullable; ask the team whether workers may exist without an assigned project before tightening it.
7. **Settings not exposed by forms:** `company_settings` has fields for the complete seeded settings object, including defaults such as currency, theme, and notification toggles. Only company information and budget threshold are saved by the visible company settings form; theme change is currently presentation-only. The schema keeps seeded settings but does not imply that the UI currently edits all of them.
8. **Dashboard monthly chart:** the frontend hard-codes July–September 2026 chart amounts and uses a fallback amount for October when its real total is zero. This is a frontend demo visualization mismatch, not missing persisted data. `get_expense_chart_data()` returns the actual monthly totals available in the ledger.
9. **Report summary quirks:** the frontend labour report table uses the attendance/availability fallback, while its summary cards default missing attendance to present. The finance report labels Materials as the largest category regardless of its rows. Database helpers provide the source records and calculated totals; the backend should not treat those fixed UI summaries as saved business facts.
10. **Empty project selector:** when there are no projects, the worker form's required project selector has no valid option; the database keeps the worker assignment nullable rather than inventing a substitute.

## Migration and test notes

Current schema version is 4. Fresh databases are created directly at version 4. Older databases run each missing numbered migration in order. Migration 4 is trigger-only and safe to repeat: it requires canonical `YYYY-MM-DD` calendar dates across projects, tasks, attendance, material last-updated dates, stock transactions, expenses, payments, and progress reports. It rejects impossible dates and noncanonical formats on inserts and date-field updates, while preserving existing rows exactly. If migration finds legacy invalid dates, initialization warns with their table, row, and value; they must be reviewed and corrected explicitly. Tests cover valid leap days, invalid month/day combinations, malformed formats, migration idempotence and preservation, plus foreign-key integrity. The full discover command also includes the existing API tests; those tests and API files were left unchanged.
